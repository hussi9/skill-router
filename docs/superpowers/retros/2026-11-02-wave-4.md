# Wave 4 retro (2026-11-02)

## What worked
- **Verifying inputs first paid off again.** It exposed that the router's logs had no project field (4.1 added one) and that whether skill names count toward the listing budget is undocumented — the plan reports both models instead of guessing.
- **The safety review earned its cost.** Five ways `apply`/`undo` could lose a user's settings (undo discarding later edits or deleting the file, writing user-level settings from `$HOME`, following symlinks, a fail-open git check, overriding explicit choices) were found by probing temp dirs and fixed before the tool ever touched a real project.
- **Honest measurement.** On the three most active projects (sub-agent use included), the bar — 80 % of project-used skills keep descriptions — was not met if names count toward the budget (3/56, 3/20, 1/22), and met in 2 of 3 only if they don't, one of them only by hiding 217 skills. Wave 4 ships as a dry-run planner.

## What did not
1. **The premise was tested last.** Four tasks of machinery were built before the simulation showed overrides barely help on a large install (skill names alone use 7,398 of the ~8,000-character budget). A one-hour feasibility spike on real data should have come first.
2. **One harness fact remains unknown:** whether names count toward the budget. It decides most results, and only the owner can observe it (`/context` in a project).
3. **Sub-agent usage was missed** until the final review (~23 % of skill use).

## Wave 5 feasibility spike (X2 applied, same day)
Simulated the listing after archiving the audit's 169 unused skills (437 → 268 routable), three most active projects:

| Budget model | Project-used skills keeping descriptions, now → after archive |
|---|---|
| names count toward the budget | 1/46 → 12/46, 1/15 → 8/15, 0/17 → 9/17 |
| names do not count | 26/46 → 26/46, 9/15 → 9/15, 11/17 → 11/17 (no change) |

Archiving is the strongest lever measured so far **if** names count toward the budget, and does nothing for descriptions if they don't (it still shortens the listing). Wave 5 is therefore gated on X1: the owner's `/context` check decides whether it is built.

## X1 answered by measurement (same day)
Ran `/context` non-interactively (`claude -p "/context"`) in the busiest project and in a scratch project:
- This machine runs a **1M-token context**, so the budget is ~10k tokens (40k characters), not the 2k the simulations assumed (they defaulted to 200k).
- The listing has **764 entries** (381 plugin, 350 user, 22 claude.ai, 11 built-in) — far more than the 437 routable skills the audit models. Only **43** carry a description; the Skills row sits exactly at the budget (9.8k ≈ 1.0 %).
- **Names count toward the budget.** In a scratch project with two plugins disabled via project `enabledPlugins`, their 51 entries left the listing (765 → 714) and two more descriptions fit (43 → 45). This also verifies that per-project `enabledPlugins` removes a plugin's skills from the listing.
- **The harness already protects frequent skills:** in the busiest project, 13 of its 15 most-used skills are described; 25 of 54 used skills overall.

## Consequences
- **Wave 5 (archive assistant) is not built.** By the measured exchange rate (~25 name entries removed per description gained), archiving the 169 unused skills would add roughly 7 descriptions. Below any reasonable bar; the audit already lists the candidates for anyone archiving by hand.
- **The simulations are retired as the source of truth.** Now-fix **X3**: measure the real listing from `/context` (opt-in, it starts a Claude session) and use it in the audit and the visibility planner instead of the simulated budget.
- **The router's role is confirmed.** With 721 of 764 entries reduced to bare names, Claude chooses rarely used skills by name alone; Jev reads every description. That is the product.

## Wave 4.x outcome
