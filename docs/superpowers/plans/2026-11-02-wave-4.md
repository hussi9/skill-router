# Wave 4 — the right descriptions survive the cap — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** For each project, make sure the skills that project actually uses keep their descriptions in Claude Code's capped skill listing, using only documented settings, reversibly, and only when the user asks.

**Architecture:** `scripts/project_usage.py` derives per-project skill usage from Claude Code transcripts (and, with a key, Jev's ranked picks recorded per project). `scripts/visibility.py` turns that into a per-project plan — which user/project skills go `name-only` via `skillOverrides`, which plugins could be disabled via `enabledPlugins` — simulates the resulting listing with the audit's `_fit_listing`, and applies or undoes it in `<project>/.claude/settings.local.json` only on an explicit command. Nothing runs from a hook.

**Tech Stack:** Python 3.11+ stdlib; pytest; Jev optional.

**Spec:** `docs/superpowers/specs/2026-11-02-skill-router-v3-vision.md` (R1, R2, R5, R7); retro `docs/superpowers/retros/2026-11-02-wave-2.md`.

## Verified inputs (input rule)

| Input | Verified how | Result |
|---|---|---|
| Listing budget and drop order | Claude Code docs, skills page | 1 % of context by default; least-used descriptions dropped first; names kept |
| `skillOverrides` values | Claude Code docs, skills page | `on` / `name-only` / `user-invocable-only` / `off`; any settings file; not for plugin skills; `/skills` writes it to `.claude/settings.local.json` |
| `enabledPlugins` per project | Claude Code docs, settings reference | Any settings file, local > project > user. Whether a disabled plugin's skills leave the listing is **not stated** → plugin changes are suggestions only, never applied |
| Per-project skill usage | `~/.claude/projects/*/*.jsonl` transcripts | 3,958 transcript files in 75 days carry `Skill` tool_use events per project directory (used to build the Wave 1 mined set) |
| Project on router events | `~/.claude/skill_router_log.jsonl` | **Not recorded** (1 of 11,383 events) → Task 4.1 starts recording a project key |

## Global Constraints

- Two modes: keyless (usage-based relevance) and Jev (adds Jev's ranked picks for the project); both tested.
- Default is a dry run. `apply` writes only `<project>/.claude/settings.local.json`, only on explicit command, with a byte-identical backup; `undo` restores it. Never writes user-level or tracked settings files; refuses if the target file is tracked by git.
- Never sets `off` (only `name-only`), never hides a skill used in that project in the last 90 days, never changes plugin settings (suggestions only).
- No hook injects anything new (R2).
- Logs and outputs carry skill names and a project key (sha256 of the resolved project path, first 12 hex chars) — never prompt text, never raw paths in committed docs.
- Tests offline; the suite-wide temp HOME and live guard apply.
- Commits intent-first, ending `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.

## Review Focus

1. **A project whose settings.local.json already has `skillOverrides`.** Expected: existing entries are preserved; plan only adds; undo restores the exact original. Test: 4.3 `test_existing_overrides_preserved_and_restored`.
2. **A skill used in the project yesterday but rare globally.** Expected: never set to name-only. Test: 4.2 `test_recently_used_in_project_is_never_hidden`.
3. **Malformed settings JSON in the project.** Expected: refuse with one line, change nothing. Test: 4.3 `test_malformed_settings_refused`.
4. **Plugin skills.** Expected: never in `skillOverrides`; listed as plugin suggestions only. Test: 4.2 `test_plugin_skills_never_overridden`.
5. **Transcripts for a deleted project directory.** Expected: skipped for apply; still counted in global usage. Test: 4.1 `test_missing_project_dir_is_skipped`.

### Task 4.2: Visibility plan

**Files:** Create `scripts/visibility.py`, `tests/test_visibility.py`.

**Interfaces:** `plan(project: Path, catalog: list[dict], usage: dict, settings: dict, jev_ranked: dict[str, int] | None = None, context_tokens: int = 200_000) -> VisibilityPlan` with fields `keep: list[str]` (keep descriptions), `name_only: list[str]` (to add to `skillOverrides`), `plugin_suggestions: list[tuple[str, int, int]]` (plugin, used in project, total), `before: dict`, `after: dict` (each `{"fit_tokens", "dropped", "project_used_kept": int, "project_used_total": int}` from `skill_audit._fit_listing`). Relevance = project usage (weight 3) + global usage (1) + Jev rank hits for the project's recent prompts (2, Jev mode only). `name_only` = lowest-relevance user/project skills, never one with project usage in 90 days, until all project-used skills fit (or no further gain).

- [ ] Steps: failing tests (`test_project_used_skills_keep_descriptions`, `test_recently_used_in_project_is_never_hidden`, `test_plugin_skills_never_overridden`, `test_jev_rank_raises_relevance`, `test_no_change_when_everything_fits`) → implement → pass → commit "Plan which skills keep their descriptions in each project".
